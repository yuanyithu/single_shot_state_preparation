# Validation 061 pre-run scientific red-team

## Deliverable and authority

This stage answers two governance questions only:

1. Which modified or untracked bytes exist in the dirty root, and which of
   those bytes agree with `origin/main` or the direct-block draft?
2. What authority does each existing validation actually possess?

It does not select a sampler, estimate `q_top`, certify a cell, reconcile a
file, authorize remote work, or create `READY_FOR_FORMAL` or
`FROZEN_HELD_OUT_PASS`.

## Mutation and ownership boundary

- The dirty root is read only. Git inspection runs with
  `GIT_OPTIONAL_LOCKS=0` to avoid optional index refresh writes.
- The dirty-root inventory excludes
  `data/expander_code/exp102/deployment_worktrees` completely.
- Registered worktrees are queried only for HEAD/branch and porcelain status;
  their untracked directories are not recursively expanded.
- Targeted comparison with the direct-block draft reads only paths already
  found in the dirty-root inventory.
- Every generated byte is confined to this validation directory. The tool
  refuses a different output path.
- No missing, differing, or duplicate file is copied, deleted, selected, or
  merged automatically. Ownership decisions remain explicit follow-up work.

## Evidence semantics

The matrix keeps the following fields separate:

- `method_internal_pass`: whether that method passed its own diagnostic gate;
- `cross_method_pass`: whether a genuinely separate mechanism agreed;
- `cell_certification`: whether a physical cell was certified;
- `formal_authority`: whether formal tuning/held-out work is authorized;
- `raw_existence`: whether sampler raw exists, not whether a README exists;
- `replay_audit`: the scope of independent replay or audit;
- `scientific_role`: primary candidate, confirmer, bound, audit, structure
  screen, preflight, or historical failure.

Unknown fields remain `UNKNOWN`; absence from canonical source is not silently
treated as failure or success. Conversely, a dirty-root directory does not
gain canonical authority merely because files exist locally.

## Mandatory factual anchors

- Validation 013 HP64 is `method_internal_pass=YES_5_OF_5`, but cross-method
  HP64/MAM comparisons are `NO_0_OF_4`; no cell is certified.
- MAM passes its own m6 diagnostic yet differs from HP64 by about 30 paired SE.
  That discrepancy is not erased by its separate m8 mixing failure.
- HP32 and HP64 share the same collapsed mechanism and cannot independently
  confirm each other.
- Validation 060 is an untracked `PRE-RUN` structure draft with no width
  report and no sampler raw. A later survivor would still be a same-family
  primary candidate, not the missing orthogonal confirmer.

## Failure conditions

The stage fails closed if:

- canonical HEAD or `origin/main` is not
  `bacf25a53870d04dc538d1caaee3336c8fe1be7a`;
- a dirty-root inventory path enters the excluded deployment subtree;
- a path cannot be represented without ambiguity;
- output would escape this validation directory; or
- the generated JSON, CSV, Markdown, and manifest fail independent checks.

No governance failure may be bypassed by editing the dirty root or by calling
an untracked draft immutable.
